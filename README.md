# پاسخ تمرین Git

## سؤال ۱: تفاوت `git merge` و `git rebase`

دستور `git merge` تغییرات دو برنچ را با هم ترکیب می‌کند. برای مثال، اگر بخواهیم تغییرات برنچ `feature` را وارد `main` کنیم، ابتدا روی `main` قرار می‌گیریم و سپس مرج را انجام می‌دهیم:

```bash
git switch main
git merge feature
```

اگر دو برنچ پس از آخرین جد مشترک، کامیت‌های متفاوتی داشته باشند، Git معمولاً یک **merge commit** با دو والد ایجاد می‌کند. بنابراین مسیر جداگانهٔ توسعهٔ هر برنچ در تاریخچه مشخص می‌ماند. البته اگر `main` از زمان جدا شدن `feature` جلو نرفته باشد، مرج می‌تواند به صورت **fast-forward** انجام شود و به کامیت مرج جدید نیازی نباشد. `merge` برای ترکیب تغییرات برنچ‌های مشترک تیم مناسب است؛ چون کامیت‌های موجود را بازنویسی نمی‌کند و تاریخچهٔ همکاری را حفظ می‌کند.

دستور `git rebase` کامیت‌های یک برنچ را بر مبنای نوک برنچ دیگری دوباره اعمال می‌کند. برای مثال:

```bash
git switch feature
git rebase main
```

در این حالت، کامیت‌های اختصاصی `feature` پس از آخرین کامیت `main` مجدد اعمال می‌شوند و تاریخچه معمولاً **خطی** می‌شود. چون کامیت‌های بازاعمال‌شده کامیت‌های جدیدی با شناسه‌های جدید هستند، `rebase` تاریخچهٔ برنچ موردنظر را بازنویسی می‌کند. این روش برای به‌روزکردن برنچ شخصی و هنوز منتشرنشدهٔ `feature` با تغییرات `main` مناسب است؛ زیرا تاریخچه را ساده‌تر و دنبال‌کردن آن را آسان‌تر می‌کند. انجام `rebase` روی کامیت‌هایی که دیگران مبنای کار خود قرار داده‌اند، بدون هماهنگی مناسب نیست.

در نتیجه، `merge` برای **حفظ ساختار واقعی انشعاب‌ها و همکاری تیمی** مناسب‌تر است و `rebase` برای **مرتب‌کردن تاریخچهٔ برنچ شخصی پیش از اشتراک‌گذاری** کاربرد بیشتری دارد.

## سؤال ۲: انتخاب بخشی از تغییرات با `hunk`

در خروجی `git diff`، هر **hunk** یک بخش از تغییرات فایل است که معمولاً چند خط اضافه‌شده، حذف‌شده یا اصلاح‌شده را همراه با تعدادی خط اطراف آن‌ها برای نمایش زمینه در بر می‌گیرد. یک فایل ممکن است چند hunk جداگانه داشته باشد؛ برای مثال، یک hunk مربوط به اصلاح توضیحات و hunk دیگر مربوط به رفع غلط املایی باشد.

ابتدا تغییرات فایل را می‌بینیم و سپس وارد حالت انتخاب تعاملی می‌شویم:

```bash
git diff -- README.md
git add -p -- README.md
```

Git هر hunk را نمایش می‌دهد و از ما می‌پرسد آیا به ناحیهٔ staging اضافه شود یا نه. گزینهٔ `y` آن بخش را stage می‌کند و `n` آن را کنار می‌گذارد. گزینهٔ `s` در صورت امکان یک hunk را به قسمت‌های کوچک‌تر تقسیم می‌کند، `e` اجازهٔ ویرایش دستی patch را می‌دهد، `q` از فرایند خارج می‌شود و `?` راهنمای گزینه‌ها را نشان می‌دهد. برای اطمینان از نتیجه می‌نویسیم:

```bash
git diff --cached -- README.md
git diff -- README.md
```

دستور اول تغییرات stage‌شده نسبت به `HEAD` را نشان می‌دهد؛ دستور دوم تغییرات باقی‌مانده در working tree نسبت به staging را نشان می‌دهد. سپس می‌توانیم فقط بخش‌های انتخاب‌شده را ثبت کنیم:

```bash
git commit -m "Update README introduction"
```

فایدهٔ این روش آن است که هر کامیت فقط یک تغییر منطقی و مرتبط را در بر می‌گیرد؛ بنابراین بازبینی کد، تشخیص علت خطا، و در صورت لزوم بازگرداندن یک تغییر مشخص آسان‌تر می‌شود.

## سؤال ۳: یافتن کامیت ایجادکنندهٔ خطا با `git bisect`

دستور `git bisect` با استفاده از جست‌وجوی دودویی، بین یک کامیت **سالم** (`good`) و یک کامیت **معیوب** (`bad`) جست‌وجو می‌کند تا نخستین کامیتی را که خطا را ایجاد کرده است پیدا کند. فرض می‌کنیم آزمونی قابل تکرار داریم که مشخص می‌کند خطا وجود دارد یا نه.

ابتدا شناسهٔ یک کامیت معیوب و یک کامیت سالمِ قدیمی‌تر را مشخص کرده و دستورات زیر را اجرا می‌کنیم:

```bash
git bisect start
git bisect bad <BAD_COMMIT>
git bisect good <GOOD_COMMIT>
```

Git یک کامیت میانی را برای آزمایش انتخاب می‌کند. پروژه را در آن نسخه بررسی می‌کنیم. اگر مشکل وجود نداشته باشد، دستور `git bisect good` و اگر مشکل وجود داشته باشد، دستور `git bisect bad` را اجرا می‌کنیم. Git هر بار بازهٔ جست‌وجو را کوچک‌تر می‌کند. این کار را ادامه می‌دهیم تا کامیت آغازگر خطا معرفی شود. در پایان:

```bash
git bisect reset
```

این دستور وضعیت checkout را به وضعیت پیش از شروع bisect برمی‌گرداند.

**مثال:** قابلیت ورود کاربران در نسخهٔ فعلی خراب است، اما می‌دانیم در نسخه‌ای قدیمی‌تر درست کار می‌کرده است. با اجرای آزمون ورود روی کامیت‌های انتخاب‌شده توسط `bisect` می‌توانیم کامیت ایجادکنندهٔ مشکل را شناسایی کنیم. اگر ۱۰۰ کامیت در بازه باشد، جست‌وجوی دودویی در حالت معمول به حدود ۷ آزمایش نیاز دارد، نه بررسی تک‌تک ۱۰۰ کامیت. این روش زمانی قابل اعتمادتر است که معیار سالم/معیوب مشخص و خطا قابل تکرار باشد.

## سؤال ۴: بررسی تغییرات پیش از کامیت

در وضعیت سؤال، بخشی از تغییرات `README.md` در staging است؛ پس از آن دوباره فایل را ویرایش کرده‌ایم، اما تغییرات جدید را stage نکرده‌ایم. برای بررسی وضعیت مخزن می‌نویسیم:

```bash
git status
git diff -- README.md
git diff --cached -- README.md
```

`git status` وضعیت فایل‌های stage‌شده، تغییرات stage‌نشده و فایل‌های untracked را نشان می‌دهد. `git diff -- README.md` تفاوت **working tree با staging** را نشان می‌دهد؛ یعنی ویرایش‌های تازه‌ای که هنوز stage نشده‌اند. `git diff --cached -- README.md` تفاوت **staging با آخرین کامیت (`HEAD`)** را نشان می‌دهد؛ یعنی محتوایی که برای کامیت بعدی آماده شده است. ممکن است در وضعیت خلاصهٔ `git status --short`، فایل با `MM README.md` دیده شود؛ یعنی هم در staging و هم در working tree تغییر دارد.

اگر اکنون کامیت معمولی زیر را اجرا کنیم:

```bash
git commit -m "Update staged README content"
```

فقط نسخهٔ ذخیره‌شده در **staging** ثبت می‌شود. ویرایش‌هایی که پس از stage کردن انجام شده‌اند، در working tree باقی می‌مانند و وارد این کامیت نمی‌شوند؛ چون `git commit` معمولی محتوای index (ناحیهٔ staging) را ثبت می‌کند. فایل‌های untracked پوشهٔ `tmp/` نیز به صورت خودکار وارد کامیت نمی‌شوند.

برای جلوگیری از stage شدن تصادفی فایل‌های موقت، در فایل `.gitignore` واقع در ریشهٔ مخزن این خط را اضافه می‌کنیم:

```gitignore
tmp/
```

این قاعده فایل‌های untracked داخل `tmp/` را نادیده می‌گیرد، اما روی فایلی که **از قبل tracked** بوده است اثری ندارد. اگر فایل‌های این پوشه قبلاً tracked شده باشند و بخواهیم بدون حذف نسخه‌های موجود روی دیسک، آن‌ها را از رهگیری Git خارج کنیم، از دستور زیر استفاده می‌کنیم و سپس تغییر را کامیت می‌کنیم:

```bash
git rm -r --cached -- tmp/
```

## سؤال ۵: حل `merge conflict` در کار گروهی

**۱. دلیل بروز conflict:** هر دو نفر پس از جدا شدن برنچ‌ها، یک خط یکسان از `README.md` را به دو صورت متفاوت تغییر داده‌اند. هنگام مرج `feature-description` در `main`، Git نمی‌تواند با اطمینان انتخاب کند کدام نسخه باید در نتیجهٔ نهایی قرار گیرد؛ در نتیجه conflict ایجاد می‌شود. تغییر هم‌زمانِ یک فایل لزوماً conflict نیست: اگر تغییرات در بخش‌های مستقل و قابل مرج باشند، Git غالباً آن‌ها را خودکار ترکیب می‌کند.

**۲. شناسایی فایل و دو نسخه:** پس از اجرای مرج، فایل‌های دارای تعارض را بررسی می‌کنیم:

```bash
git switch main
git merge feature-description
git status
git diff --name-only --diff-filter=U
```

Git در متن فایل معمولاً نشانه‌هایی شبیه موارد زیر می‌گذارد:

```text
<<<<<<< HEAD
متن موجود در main
=======
متن موجود در feature-description
>>>>>>> feature-description
```

بخش بالای `=======` نسخهٔ برنچ فعلی (`main` یا **ours**) و بخش پایین نسخهٔ برنچ درحال‌مرج (`feature-description` یا **theirs**) است. برای دیدن نسخه‌های کامل ثبت‌شده در index هنگام تعارض نیز می‌توان نوشت:

```bash
git show :2:README.md   # ours: main
git show :3:README.md   # theirs: feature-description
```

**۳. حل تعارض و تکمیل مرج:** چون اطلاعات هر دو تغییر باید حفظ شود، فایل `README.md` را باز می‌کنیم، متن‌ها را به شکلی سازگار در متن نهایی ترکیب می‌کنیم و تمام خطوط `<<<<<<<`، `=======` و `>>>>>>>` مربوط به تعارض را حذف می‌کنیم. سپس بررسی می‌کنیم که نشانگرهای تعارض در فایل باقی نمانده باشند و نتیجه از نظر معنایی درست باشد:

```bash
git grep -n -e '^<<<<<<< ' -e '^=======$' -e '^>>>>>>> ' -- README.md
git add -- README.md
git diff --cached --check
git status
git commit -m "Merge feature-description into main"
```

اگر `git grep` هیچ موردی پیدا نکند و `git diff --cached --check` خطایی گزارش نکند، احتمال باقی‌ماندن نشانگرهای معمول تعارض بسیار کمتر می‌شود. افزون بر این، باید متن نهایی را دستی بازبینی کنیم؛ صرف نبود نشانگرها به معنی درست بودن محتوای مرج‌شده نیست. اجرای `git add` به Git اعلام می‌کند که تعارض این فایل حل شده است. پس از برطرف شدن همهٔ تعارض‌ها، `git commit` عملیات merge را با ثبت کامیت مرج تکمیل می‌کند.

**۴. لغو مرج:** اگر پیش از نهایی شدن مرج تصمیم بگیریم که فعلاً نباید انجام شود، از دستور زیر استفاده می‌کنیم:

```bash
git merge --abort
```

با توجه به اینکه working tree پیش از مرج clean بوده است، این دستور معمولاً مخزن را به وضعیت پیش از شروع merge بازمی‌گرداند.

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

**موقعیت 1 ـ کنار گذاشتن تغییرات stage‌نشدهٔ یک فایل:** چون تغییرات `notes.txt` هنوز stage نشده‌اند و نسخهٔ staging با `HEAD` یکسان است، دستور زیر کافی است:

```bash
git restore --worktree -- notes.txt
```

این دستور فقط فایل `notes.txt` را در working tree با نسخهٔ staging جایگزین می‌کند؛ در این سؤال یعنی آن را به نسخهٔ آخرین کامیت برمی‌گرداند. staging، فایل‌های دیگر و تاریخچهٔ کامیت‌ها تغییری نمی‌کنند. **تغییرات stage‌نشدهٔ این فایل از دست می‌روند**؛ بنابراین فقط هنگامی باید از آن استفاده کرد که واقعاً دیگر به آن تغییرات نیاز نداریم.

**موقعیت 2 ـ خارج کردن فایل از staging بدون حذف ویرایش‌ها:**

```bash
git restore --staged -- notes.txt
```

این دستور نسخهٔ فایل در staging را به محتوای `HEAD` بازمی‌گرداند، اما **working tree را تغییر نمی‌دهد**؛ پس ویرایش‌های انجام‌شده روی دیسک حفظ می‌شوند و صرفاً دیگر برای کامیت بعدی stage نیستند. تاریخچه نیز تغییری نمی‌کند.

**موقعیت 3 ـ خنثی کردن کامیت منتشرشده در برنچ مشترک:** روش مناسب `git revert` است:

```bash
git switch main
git revert <BAD_COMMIT_HASH>
git push origin main
```

`git revert` یک **کامیت جدید** ایجاد می‌کند که اثر تغییرات کامیت اشتباه را معکوس می‌کند. کامیت اشتباه و سابقهٔ اصلی همچنان در تاریخچه باقی می‌مانند؛ در نتیجه دیگر اعضای تیم می‌توانند کامیت اصلاحی را به شکل معمول دریافت کنند. با فرض نبود conflict و clean بودن وضعیت اولیه، working tree و staging پس از ثبت کامیت جدید دوباره clean خواهند بود. در مقابل، حذف کامیت با `git reset` و انتشار تاریخچهٔ بازنویسی‌شده با `force push` می‌تواند مبنای برنچ‌های هم‌تیمی‌ها را تغییر دهد، باعث واگرایی تاریخچه شود و بازیابی/هماهنگ‌سازی تغییرات را دشوار کند؛ به همین دلیل برای کامیت منتشرشده روی `main` انتخاب مناسبی نیست.
